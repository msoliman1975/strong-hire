How the Strong Hire agents work

This guide covers every LLM-driven component in Strong Hire: what each agent does, how it is wired, what it remembers, which guardrails surround it, and how its actions and reasoning are traced and monitored. It was written from the code on main. File references point to the repo.

The core idea in one sentence. Strong Hire is not one free-roaming agent. It is a set of role-based agents (extractor, planner, interviewer, scorer, coach). Each one is wrapped in a deterministic agent harness: code that decides the flow, checks every output, and keeps the state. The code is in charge. The model only fills in what to say or how to judge.
What "agent" means in this guide: one gateway role plus the code loop around it (prompts, context, checks, retries, persistence). These are workflow agents, not autonomous ones: none of them picks its own tools or next step, and none calls another agent. Code and job chains decide the next action every time.
What "agent harness" means here: everything around the model call. It builds the context (brief, transcript window, story state), runs the loop, enforces the rules (controller, output guard, conduct checks), validates and grounds outputs, retries or falls back, and persists state, traces and usage. It is more controlling than a typical agent harness, which runs a loop where the model picks the next tool call. Here the harness picks the next step, and the model fills in one bounded part of it. Not to be confused with the eval harness (strong_evals, HarnessInterviewer), which is a test driver that runs agents against scripted or simulated candidates.

Five rules that explain most of the design

1. Everything goes through one gateway

Only strong_core.gateway may import a model SDK (Pydantic AI). The code asks for a role, and config/models.<profile>.yaml picks the model. An architecture test enforces this.

2. The controller owns the flow

Phase changes, the clock, probe limits, when the session ends: all of these are code (SessionController). The interviewer model never decides to end the interview.

3. Judgment and arithmetic are separate

The scorer model gives rubric scores with quotes. Code computes the hire signal. The gap match score and story missing parts are also computed in code.

4. Every output is checked

Pydantic schemas (one gateway retry), the output guard, quote verification, fact grounding and fixed fallback lines. A weak model degrades the result but never breaks the flow.

5. Prompts are versioned files

prompts/<role>/<name>[.<tier>].v<N>.txt. Each message carries a prompt_ref, and outputs store the refs (for example Scorecard.rubric_version).

6. Tests never call a real model

MODEL_PROFILE=fake replays fixtures from gateway/fixtures/<role>/. CI is deterministic, and evals can switch to real profiles.

Each stage is triggered by an API route that enqueues an Arq job (job ids such as jt:<id>, ga:<id>, brief:<sid>:<hex>, score:<sid>:<hex>). The live interview is the only stage on the latency-critical path, and it reads only the compact brief.

4. Model gateway, profiles and prompts

The gateway is the agents' shared "brain stem". Every call takes the same path, so usage, cost and prompt versions are captured in one place.

Model profiles: pick one to see the role mapping

Prompt loader (PL-5, PL-6)

How a prompt is chosen

  1. load_prompt(role, name) looks in prompts/<role>/.
  2. It reads the tier of the model that serves the role (capabilities(role).tier: small, medium or large). It never looks at the model name.
  3. If <name>.<tier>.vN.txt exists, that variant wins. Otherwise the default variant <name>.vN.txt is used.
  4. The highest version wins, unless the caller pins one.
  5. $placeholders are filled with string.Template. A missing value raises an error.
  6. .message(role, ...) returns a Message with prompt_ref set, for example interviewer/turn.small.v3.

The fake model (tests and CI)

FakeBackend answers complete() with the first match, in this order:

  1. fixtures/<role>/<messages-hash>.json|.txt: an exact recording. The hash is sha256 of [[role, content], ...], first 16 hex characters.
  2. <role>/<OutputType>.json: the default output for that contract.
  3. <role>/text.txt for plain-text replies.

If nothing matches, FakeFixtureMissingError names the file to add. RecordingGateway (gateway/recorder.py) wraps a real gateway and saves every call as a replayable fixture.

5. The interviewer agent (deep dive)

The package packages/interview (strong_interview) holds three collaborating parts. The voice agent, the text channel and the eval harness all run this same code.

SessionController

controller.py

A pure-code state machine. It decides the next Move (greet, ask, probe, curveball, warn, wrap up and so on) and records why (the Why enum) for the traces.

Interviewer

interviewer.py

Turns a move into words (say), chooses probe or move on (decide), and checks conduct (check_answer). All three use the interviewer role.

InterviewRunner

runner.py

Keeps the transcript, sequences each candidate turn, runs the checks in parallel, emits trace records, and recovers when a turn fails.

5.4 What the interviewer sees (its prompt)

System: interviewer/turn (or a type variant)

Recruiter screen uses turn_recruiter_screen. Role-play uses turn_role_play with the hidden buyer brief.

  • Persona: name, interview type, level, company line, tone, pushback style, closing style, seniority bar
  • Hard rules: speak only the words to say, at most 2 sentences and max_words (35, or 30 on small tier), one question, no feedback, no meta talk
  • Session facts it may share (company, job, team, notes). For anything else it says it doesn't know.
  • The meaning of each move: greet, small_talk, agenda, ask, probe, curveball, …

The brief is the interviewer's compressed knowledge. The interviewer never sees the raw resume or posting. The planner condenses them into an InterviewerBrief of at most about 1500 tokens: 4–6 target competencies, 6–12 ranked questions with probe hints, probe areas, persona, time plan, curveball and seniority bar. This keeps the prompts short and the latency low.

5.5 Special modes

Coach mode (IV-8)

The candidate can pause, ask for a hint (at most 2 per question) or redo a question. CoachNotAllowedError outside Coach mode.

Custom sessions (CU-4)

Categories run in the candidate's order. Must-ask questions are guaranteed by the controller, never the model, using a time reserve. Verbatim questions: the model writes only a lead-in of 12 words or fewer, and the code appends the exact text.

Role-play (RP-5/6)

The interviewer plays a buyer from a hidden RolePlayBrief (pains, budget, objections). The buyer has its own decide prompt with triggers: needs_discovery, objection_unresolved, no_value_link and no_next_step.

Conduct (IV-12)

Strikes 1 and 2 get fixed warning lines, and the same question stays open. Strike 3 gets a fixed closing line and the session ends.

Dropped connection (IV-9)

hold() stops the clock. Within 120 s the agent says "welcome back" and repeats its last line. rebuild(turns) can rebuild controller state from the saved transcript.

Take-back (barge-in)

If the candidate keeps talking while a reply is being prepared, runner.rollback(checkpoint) restores the controller snapshot and removes the turns. A rollback trace is written.

6. Voice pipeline

The voice agent (apps/voice, LiveKit Agents) handles audio only. It uses LiveKit for VAD, end-of-turn detection and barge-in, but suppresses LiveKit's own LLM reply (raise StopResponse) and hands the text to the shared InterviewRunner.

Room dispatch (agent.py)

  • session-<uuid> → real interview. Sets the DB usage sink, plus log_context and usage_context(org, session) before connecting, so every task inherits them.
  • coach-<uuid> → voice coach. It relays each turn to the API's internal coach endpoint and keeps no LLM state of its own.
  • Any other name → latency spike room.

Turn-taking details (turns.py)

  • Replies are prepared one at a time, under a lock.
  • If STT is still busy at end of turn, the reply waits so the rest of the answer can join.
  • "Let me think" phrases → the fixed TAKE_YOUR_TIME line and a check-in after 60 s of silence.
  • Prep-time requests (IV-11): hold the clock for 1–3 minutes.
  • Data channel topics coach (hint, redo, pause, end…) and session (live state, captions).

At the end, VoiceInterview.finish flushes the turns, saves prompt_version, flushes the traces (5 s limit), then POSTs /internal/sessions/{id}/end. The API bills the minutes and enqueues scoring.

Planner jobs

Gap analysis (GA-1..3)

In: posting text, requirements r1..rn (up to 12 must-haves and 6 nice-to-haves), family competencies, a compact resume, user notes (1500 characters), company line.

Model: GapAssessment, with each requirement rated 0–3 plus evidence.

Code: unrated items count as 0. A rating of 2 or more without resume evidence is capped at 1. Strengths without evidence are dropped. match = 0.7 × requirements + 0.3 × competencies.

Out: gap_analyses (score, breakdown, session plan, model_version).

Interviewer brief (on session create)

In: the latest ready gap analysis, the resume, the company profile version (or an approved auto-profile), family guidance, level bar, difficulty, tone, duration.

Model: BriefDraft (6–12 questions + curveball), or RolePlayDraft.

Code: repairs ids, forces every target competency to be covered, drops off-limits recruiter questions (salary history, protected traits), sets probes by difficulty, adds the curveball only on Tough, builds the time plan, trims to 1500 tokens. Tone comes from a parsed prompt file the planner never sees.

Out: sessions.brief_json. 2 tries, then the session is FAILED.

Story fit (ST-5)

Matches the user's stories (up to 30) to the job's tested skills: strong, thin or missing. Small tier makes one call per skill. The result is cached by an input hash in role_story_fits, and can be reused across roles with the same hash.

Profiles are not built by agents at runtime

Curated company profiles are researched offline, reviewed, versioned and imported. No research runs inside the app or during an interview. Each session records the profile version it used, so scores stay explainable.

8. The scorer agent

The scorer is deliberately separate from the interviewer: it reads the whole transcript afterwards, like a debrief panel. The live model therefore never softens its judgment mid-conversation, and scoring can use a stronger, slower model.

Bands: ≥ 3.5 Strong Hire · ≥ 3.0 Hire · ≥ 2.6 Lean Hire · ≥ 2.0 Lean No Hire · else No Hire. Rules use each average rounded half up to a whole point. In company mode, values_share of the average comes from company-value scores.

After the scorecard

  • Delivery metrics (words per minute, fillers) come from voice timestamps. This is code, not a model.
  • Progress snapshots (one per competency) are written only for Realistic sessions that are not minis.
  • Story match (ST-6): for each answer, which library story it used (STORY: S3 | NONE, FIX: …). A Realistic answer that scores 3 or more on a real-model profile makes the story Proven (ST-7).
  • Suggestions: the coach role proposes story tunes and new stories (see section 9).
  • Takes (CO-7): one telling of a story is scored by the same scorer with a synthetic one-question brief. The rationale is written in code.

9. The coach agent and suggestions

The coach helps the candidate build interview stories (context, stakes, action, result, reflection). Its defining rule is CO-3: it may only record what the candidate actually said. Every story update must quote the candidate's words.

What to ask next is chosen in code (CO-4)

In order: concrete example (context) → stakes → own role (asked when the action says "we" but not "I") → measurable result (asked when there is no number) → trade-offs → reflection. The model is told which one thing to ask about.

Styles (CO-5)

style_gentle or style_direct is a section of the system prompt. Code also enforces it: a direct reply keeps only the question, and a gentle reply that praises ("a meaningful outcome") becomes "Thank you."

No agent has hidden or long-lived "chat memory", and there is no vector store or embeddings. Every model call is stateless. Memory is explicit data that code assembles into each prompt from Postgres, in layers.

Durability and recovery

Failed turn

respond() takes a checkpoint. If a model error, a save error or a timeout happens before anything is said, the controller is restored and an unsaved turn is popped. The candidate can resend the same answer.

Reconnect

The clock is held. The live state stays in the voice process for 120 s. rebuild(turns) can rebuild the queue, the asked and dropped questions, the probes used and the clock from the transcript.

Text-channel caveat

Text runners live in the API process (app.state.text_runners), and only in local and test environments. If the API restarts, an open text session must be ended.

Retention: interviewer traces and voice timings are kept 90 days. Ops samples and error events are kept 30 days. Transcripts and error groups are kept. Audio is never written by the voice agent.

12. Tracing and monitoring

Observability is built in-app on Postgres and Redis. The admin spec says: "There is no Grafana, Prometheus, Loki or Sentry". No OpenTelemetry, Sentry, Langfuse or LangSmith code is imported anywhere. (The original docs/spec.md still lists Sentry, Prometheus, PostHog and OTel as plans. The admin spec superseded that.)

12.3 Default alert rules

API down · Worker or voice down · Dependency down · Disk 85%/95% · Memory 90% · Session failures > 5% · Voice p95 > 1500 ms over 30 min · Scoring stuck · Spend ≥ 80% and 100% of the daily cap · New error group · Stripe webhooks silent > 48 h. Critical alerts re-notify every 4 h, warnings every 24 h.

12.4 Correlation: following one session across services

Use session_id as the join key. It appears on turns, interviewer_traces, usage_events, voice_turn_timings, error_events, every log line (ContextVar, or derived from the LiveKit room name), and the scorecard. request_id joins an API request or worker job to its logs and errors.

13. Evals, the AI candidate and the judge

Two harnesses test the agents. Keep them apart when you explain them.

In-process eval harness (evals/)

python -m strong_evals run --suite … --gate. Calls the interviewer, planner, scorer and coach as library code. Profiles: fake, tiny, local, hosted, claude. --record saves fixtures.

  • Gold set: scripted transcripts with human labels (median of the raters)
  • Simulated candidates: strong, average or weak
  • Reports in evals/reports/*.html|json, with the git sha, the role → alias map and the prompt refs

Live AI-candidate sim (apps/sim, P13)

Drives the deployed app over HTTPS or LiveKit as a real user would. The candidate uses a different provider from the interviewer on purpose. A judge model then grades the interviewer.

  • Persona × quality × behavior: off_topic, prompt_injection, interrupts, drops_connection, argues, silent…
  • Budget isolated with its own LiteLLM key ($5/day), gated, started from the admin UI
  • Results saved in run folders (transcript, audio, judge, debrief, meta)

14. Q&A cheat sheet

Short answers to questions you are likely to get.

Is this a multi-agent system? Do agents talk to each other?

Not directly. The agents form a pipeline that hands typed artifacts over through Postgres: extractor → JobPosting/Resume → planner → GapAnalysis, InterviewerBrief → interviewer → turns → scorer → Scorecard → coach suggestions. Arq jobs and API routes do the orchestration. No agent calls another agent, and none chooses tools on its own.

Do the agents use tool calling or autonomous planning?

No. "Tool output" is only a way to get structured JSON when a model supports tools. The next action is always chosen in code (controller moves, coach "ask for", job chains).

How does the interviewer "remember" earlier answers?

Each call gets the brief plus the last 16 turns (6 on small models). The controller keeps structured state (questions asked, probes used, which gaps were probed). The full transcript is in the turns table, and the scorer reads all of it.

What prevents the interviewer from giving feedback or leaking its reasoning?

The prompt forbids it, and the deterministic output guard enforces it. The guard removes meta sentences and evaluative clauses, retries once with a stricter instruction, then says a fixed line. Every step is traced with guard.rules and guard.action.

Who decides when the interview ends?

Only the SessionController: the time plan, no questions left, the candidate questions limit, the conduct limit, or an explicit end. The model never does.

How is the hire signal computed? Can the model change it?

The model gives per-question rubric scores (1–4) with quotes. Code verifies the quotes, averages per competency, applies the profile weights (and the values share), maps the average to a band, and applies the hard rules. The model then writes a 3–5 sentence rationale for that signal. A rationale that names another signal is replaced by a code-built one.

How do you see why the interviewer asked a given follow-up?

Open the session in admin (training consent required). Find the decide trace (missing list), then the say trace with reason.why = ["model_chose_probe"], the timer state, the full prompt messages, the raw reply and the spoken text.

How is cost tracked?

Every gateway call made inside a usage_context writes a usage_events row (role, units, cost from the LiteLLM price table, cost_known). Interviewer traces also carry per-call cost. Admin Spend compares this with the daily spend cap, which can block new sessions (OC-3).

How do you switch models (for example to a bigger interviewer)?

Change MODEL_PROFILE, or set MODEL_ROLE_INTERVIEWER=<alias>, or edit config/models.<profile>.yaml. The capability tier selects prompt variants automatically. No code changes, because code never names a model. Re-run the eval gates afterwards.

How is prompt injection handled?

Inputs are sanitized, candidate text is JSON-quoted as data, custom questions pass 21 regexes plus a model check, instruction-like output items are dropped, conduct checks run, and the controller owns the flow, so the model has no control over phases or scoring. The sim has a prompt_injection behavior and an injection judge rule.

What happens if the LLM is down mid-interview?

decide fails → move on. check_answer fails → the turn counts as OK. A say retry fails → a fixed line. A first say failure is raised: the runner restores its checkpoint so the candidate can resend, and the text API answers 504. Errors are logged, grouped in the error inbox, and recorded in the trace's error field.

Why are interviewer and scorer separate?

So the live model never softens its judgment mid-conversation, the scorer can be a slower and stronger model, and live latency stays low because the interviewer only reads the compact brief.

How do tests run without models?

MODEL_PROFILE=fake: FakeBackend replays exact recordings by messages hash, else a default fixture per output type, else text.txt. A missing fixture error names the file to add.

15. Known gaps (as of this writing)

  • Only interviewer calls are traced. Extractor, planner, scorer and coach calls have usage rows but no prompt or reply traces and no latency. Ops Performance shows them as "not measured".
  • Some provenance is not persisted. Brief model_version and refs, and extraction provenance, live only in Arq results (24 h). Story match persists no prompt ref.
  • Story fit and tailoring run without a usage_context (gap/story_fit.py), so they write no usage_events and have no request_id log context.
  • Coach usage rows carry no session_id (org only).
  • The auto-profile job bypasses the sim-org key (profiles/jobs.py).
  • The text channel's runners are in-process and lost on API restart (dev and test only).
  • The sim judge has no role-play rules, and admin-started sim runs can't run role-play yet.
  • The in-process eval candidate uses Role.PLANNER, while the live sim candidate uses Role.CANDIDATE.
  • docs/spec.md still lists Sentry, Prometheus, OTel and PostHog. The implementation follows docs/admin-spec.md (in-app only).
